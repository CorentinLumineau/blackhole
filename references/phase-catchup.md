# Phase — Catchup

Binding playbook for the `catchup` mode (`SKILL.md` § Modes): burn the weekly quota down to the pace
floor by running the normal campaign, gated by `usage-budget.ts --floor`. The decision and the
floor math are `documentation/decisions/ADR-054-catchup-mode-quota-pacing.md` (C1-C3); this file
owns the steps. It composes with the five phase playbooks and replaces none of them. A catchup is
a `run`: it takes the same launch gate (`launch-gate.md`, catchup form) and drains with `stop`
(`phase-stop.md`).

## When to use

The owner (or a scheduled task) wants the unused share of this week's allowance spent on backlog
work. Use `run` instead when no quota target matters.

Set `catchup.lane` per account before a second account runs on the same repo (the Pacing row reads
`lane unset` until then): dispatch claims each issue under that lane through
`orchestrator-dispatch.md` § Lane claim and release.

## Steps

1. **Resolve the run context** (`run-context.md`), as for any `run`, then run the target check
   (`launch-gate.md` § Target check): print the resolved repository and campaign directory, and ask
   Continue here / Stop before going on when the session's stated target names another repository.
2. **Read usage.** `bun run scripts/usage.ts` prints one normalized reading. On a host with only an app
   usage tool (no statusline cache), write that tool's output to a file as is (the raw desktop `get_usage` payload is accepted) and pass it to `usage` and
   `pace-floor` as `--usage <file>`, and to the gate as `--usage-file <file>` (the gate's own
   `--usage` takes inline JSON).
3. **Compute the floor.** `bun run scripts/pace-floor.ts [--usage <file>]` prints `status`, `floor_pct`,
   `elapsed_h`, `target_pct` and `shortfall_pct`. `unreadable` or `no-weekly` means log the reason and
   exit. A `floor_pct` of 0 (the instant the week starts) is a valid floor: pass it to the gate, which
   returns `STOP-CAMPAIGN`.
4. **Gate.** `bun run scripts/usage-budget.ts --parallel-max <n> --floor <pct> [--usage-file <file>]`
   (the sibling pace gate, `pace-gate.ts`, is unchanged and runs beside it in every spawn round).
   `--floor` is for this invocation only, forces the gate on and never writes `config.json`:

   | Verdict | Do |
   |---------|----|
   | `GO` | Continue with `workers` |
   | `STOP-CAMPAIGN` | Usage is at or above the floor: log it and exit; no wake |
   | `SKIP` | Usage unreadable, or no weekly window or plan limits (fail-closed): log the reason and exit |
   | `PACE-WAIT`, `NO-SPAWN`, `STOP-WORKERS` | Log the reason and exit; the next scheduled start decides again |

   No ready work is its own skip reason: log it and exit.
5. **Launch gate.** Run `launch-gate.md` in its catchup form: the 13 rows with the catchup Pacing row, the
   preset pre-filled, every value adjustable for this invocation through the summary flags. An
   `--unattended` invocation passes `--unattended` to the summary, which makes it print-only.
6. **Run the normal campaign** with the floor pinned in the orchestrator's spawn text, so every
   spawn round runs `usage-budget.ts --floor <pct> [--usage-file <file>]` in place of the plain call in
   `orchestrator-runtime.md` § Spawn step 1. The floor is recomputed at every start and wake (it
   grows with the clock); an owner-adjusted floor stays pinned for the invocation. A `SKIP` in a
   later round is a `STOP-CAMPAIGN`: drain, no wake (`phase-stop.md` § Usage stop).

## Stop

`stop` drains a catchup exactly like a run, in all three tiers (`phase-stop.md`).

## Scheduled task

The schedule is ADR-054's: weekdays about 18:00, 23:00 and 04:00, weekends every 5 hours. The task
lives outside the repo (a desktop scheduled task or a cloud routine). One prompt per account:

```text
Write the app's usage tool output to <usage-file>. Then run /blackhole catchup --unattended with
--usage-file <usage-file>. Owner questions are parked for /blackhole decide.
```

`--unattended` is for this invocation only: the launch summary runs as
`campaign-status.ts --summary --mode catchup --unattended …`, so the gate is print-only, every row
counts as accepted and the `--floor` gate decides (`launch-gate.md` § Print-only mode). Nothing is
stored, so an interactive `/blackhole catchup` the owner types still asks. The run holds
keep-awake while a worker is in flight or a wake is armed, and re-arms its own wake-ups
(`keep-awake.md`). Copy the task per account and set `catchup.lane` in that account's config.
A task written before the sleep-mode retirement still says "turn sleep mode on": replace it with
the prompt above (the old first sentence now fails with a line naming `--unattended`).
