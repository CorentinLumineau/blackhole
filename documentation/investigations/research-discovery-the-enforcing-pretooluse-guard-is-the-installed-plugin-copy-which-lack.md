# Research: how does an installed Claude Code plugin's cache get refreshed after its source repo changes?

## Executive Summary

All three questions are answered directly by Claude Code's own documentation (`code.claude.com/docs`), fetched and quoted below, plus cross-checked against three real, verified GitHub issues in `anthropics/claude-code`.

1. **What triggers a refresh**: `/plugin marketplace update <name>` (catalog only), background auto-update (session-start + up to 10 min delay, **off by default for third-party/local-dev marketplaces**), `/plugin install`/`/reload-plugins` (activation, not necessarily re-fetch), or the documented manual fallback `rm -rf ~/.claude/plugins/cache && restart && reinstall`. There is no refresh that is unconditional on content — every path is gated by the resolved **version**.
2. **Version-keyed vs. content-addressed — the crux question**: **version-keyed, confirmed directly from the reference docs, for every source type including local/relative-path sources like blackhole's `source: "."`**, with one narrow exception (`command` sources). An explicit `version` field in `plugin.json` "pins the plugin to that version string, so users only receive updates when you bump it." Blackhole's `.claude-plugin/plugin.json` declares an explicit version, so this is the operative rule for blackhole's installed copy, not a fallback rule. This makes "bump the version on every `templates/hooks/**` change" a documented, structural necessity — not a discretionary tidy-up — as long as blackhole keeps an explicit `version` field.
3. **Documented dev/local update path**: `--plugin-dir <path>` is the one documented mechanism that bypasses the cache entirely — Claude Code loads plugin content directly from disk for that session, no install step, no version check. This is explicitly framed as a development/testing flag, not a production deployment path, and it is a different install mode from `/plugin marketplace add` + `/plugin install` (which blackhole's `CLAUDE.md` documents as the install path and which does go through the cache).

Everything above is directly documented; nothing here required guessing at internal mechanics. One narrow point is explicitly flagged as inferred, not documented, in §2.

## Findings

### Q1 — What triggers a cache refresh

Source: `code.claude.com/docs/en/discover-plugins.md` (fetched in full).

- **`/plugin marketplace update <marketplace-name>`** (or `claude plugin marketplace update` from the shell) — "Refresh plugin listings from a marketplace." This refreshes the marketplace **catalog** (`marketplace.json`), i.e. what versions/plugins are known to exist — not, by itself, the already-cached content of an already-installed plugin at a given version.
- **Auto-update** — "Claude Code can automatically update marketplaces and their installed plugins in the background after startup... Claude Code checks for marketplace and plugin updates after your session starts, with a random delay of up to ten minutes... If any plugins were updated, you'll see a notification prompting you to run `/reload-plugins`, or the new versions load on your next launch." Critically: **"`claude-plugins-official` and most other official Anthropic marketplaces have auto-update enabled by default. Third-party and local development marketplaces have auto-update disabled by default."** Blackhole's marketplace (added via `/plugin marketplace add https://github.com/CorentinLumineau/blackhole`, per this repo's `CLAUDE.md`) is a third-party marketplace. Unless the campaign operator explicitly enabled auto-update for it (`/plugin` → Marketplaces → toggle), **auto-update is off by default for this exact marketplace**, meaning the 10-minute background check may simply never have been running.
- **`/plugin install plugin-name@marketplace-name`** (named-marketplace form) — "Claude Code refreshes that marketplace before the lookup," with listed exceptions (not added from a git host/URL, seed-directory-supplied, refreshed within the last 30 seconds, `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` set, or managed-settings block). This refreshes the **catalog** before resolving which version to install — it is not itself a guarantee that new plugin *content* under an unchanged version string gets re-fetched (see Q2: the resolved version is what's compared, and content changes under a stable version string produce no signal to refresh).
- **`/reload-plugins`** — "applies enabled/disabled changes and installs without restarting." This activates already-fetched plugin state; it is not a fetch/refresh step.
- **Documented manual troubleshooting fallback** (`code.claude.com/docs/en/discover-plugins.md`, Troubleshooting section): *"If plugin skills don't appear, clear the cache with `rm -rf ~/.claude/plugins/cache`, restart Claude Code, and reinstall the plugin."* This is the one documented path that unconditionally discards cached content regardless of version string.
- Version pinning for `command`-source plugins is the one type with a different, hash-based cadence: "Claude Code updates plugins that have a `command` source on a separate cadence... it re-runs the command once per session and installs the output as a new plugin version when its hash has changed." Blackhole is not a `command` source (it's a git-repo/local-path `source: "."` entry per ADR-009), so this cadence does not apply here.

**Independent corroboration (GitHub issues, verified via `gh issue view --repo anthropics/claude-code`, not fabricated)**: #17361 "Plugin cache never refreshes - autoUpdate doesn't update what Claude reads" (open), #72616 "Directory-source marketplace: cached marketplace.json not refreshed on update, so plugin version stays stale" (closed), #61954 "claude plugin update reports 'at latest' but cache stays stale vs refreshed marketplace (path-based plugins)" (closed). These are user-facing reports of exactly this failure mode across marketplace source types, consistent with the documented version-gating below rather than contradicting it.

### Q2 — Version-keyed or content-addressed? (the crux)

Source: `code.claude.com/docs/en/plugins-reference.md` (fetched in full) and `code.claude.com/docs/en/plugin-marketplaces.md` (fetched in full).

**Confirmed: version-keyed, for every source type except `command` sources, whenever `plugin.json` (or the marketplace entry) declares an explicit `version`.** Direct quote, `plugins-reference.md`, `version` field under Metadata fields:

> "Optional. Semantic version. Setting this pins the plugin to that version string, so users only receive updates when you bump it, except for a [`command` source]... If also set in the marketplace entry, `plugin.json` wins. If omitted, the version comes from the next source in [Version management]."

And from `plugin-marketplaces.md`, stated generally (not archive-source-scoped, despite that section's heading):

> "Setting `version` pins the plugin for every source type except [`command`](...), whose version always includes a hash of what the command produced. If you declare `"version": "1.0.0"` in `plugin.json` and push new commits without changing that string, existing users of those sources keep the cached copy, because Claude Code sees the same version. Bump the field on every release, or omit it to fall back to the resolved version."

Cache directory structure, `plugins-reference.md` (Plugin caching and file resolution):

> "Plugins are copied to `~/.claude/plugins/cache` rather than used in place, except for `command` sources in link mode. Each installed version is a separate directory in the cache, grouped by marketplace and plugin and **named for the resolved version**, with its own copy of the plugin's files."

So the cache key is literally the resolved version string (`~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`, matching the incident's own evidence). It is **not** content-addressed (not a hash of the source tree) for any source type that declares an explicit `version` — that includes local/relative-path sources (`"source": "."` or `"source": "./subdir"`), git/GitHub sources, and archive sources alike. The only source type with automatic, hash-based versioning regardless of a declared `version` field is `command` sources.

**What this means for blackhole concretely**: `.claude-plugin/plugin.json` declares `"version": "0.21.0"` explicitly (confirmed by this repo's build output and the issue's own evidence). Per the quotes above, that declared value is the operative version for cache-key purposes — full stop, for a `source: "."` local-path entry exactly as much as for a git or archive source. Two commits landed new hook content under the unchanged string `0.21.0` (`9aa929a2`, `e7a47b73`); by the documented mechanism, **no refresh path — catalog update, auto-update, or reinstall — has any signal that content changed**, because none of them compare content, only the version string. This is not merely "how it probably works" — it is the literal mechanism the reference docs describe for exactly this configuration.

**One explicitly-flagged gap**: the docs describe, for *omitted*-version sources, a fallback resolution order (git sources fall back to resolved commit SHA: *"For git-based sources, if you omit `version`, Claude Code uses the source's resolved commit SHA, so users get an update whenever that commit changes"*). This fallback is **not relevant to blackhole today**, since blackhole declares an explicit version, but it is directly relevant to any remediation that considers *removing* the explicit `version` field to get automatic commit-SHA-based cache keys for a local/git-adjacent `source: "."` entry — the docs describe this fallback for git-based sources (`github`, `url`, `git-subdir`) explicitly; whether a bare local relative-path source (`"source": "."`, not one of those three named git-based types) resolves the same way when unversioned is **not stated verbatim in the fetched text** and is left undetermined here rather than assumed. This is worth a follow-up doc fetch (`Version management` section proper, `plugins-reference.md#version-management`) if the campaign considers that remediation path.

**Also explicitly flagged as inference, not confirmed by the docs**: whether a plain `/plugin uninstall` + `/plugin install` (reinstall) at the *same* version string forces a fresh copy from source into the same-named cache directory, or reuses/no-ops against the existing directory for that resolved version. The docs state this behavior only for `/plugin update` and auto-update ("if the resolved version matches what a user already has, `/plugin update` and auto-update skip the plugin"); they do not state it for a manual uninstall+install cycle. Given the cache is explicitly "named for the resolved version" and version is the sole signal used throughout, it would be consistent for a same-version reinstall to also reuse the existing directory contents rather than re-fetch — but this specific case is not stated in the fetched documentation, so it is marked here as **inferred, not confirmed**. The one documented action that unconditionally discards cache regardless of version is the manual `rm -rf ~/.claude/plugins/cache` fallback quoted under Q1.

### Q3 — Documented update path for a local/dev plugin from a git source

Source: `code.claude.com/docs/en/plugins.md` (fetched in full).

- **`--plugin-dir <path>`** is the one documented mechanism that bypasses the marketplace/cache pipeline entirely: *"Use the `--plugin-dir` flag to test plugins during development. This loads your plugin directly without requiring installation."* And: *"When a `--plugin-dir` plugin has the same name as an installed marketplace plugin, the local copy takes precedence for that session."* Local edits are picked up live via `/reload-plugins` (no version bump, no reinstall) while running under `--plugin-dir`. This is explicitly scoped as development tooling: *"The `--plugin-dir` flag is useful for development and testing. When you're ready to share your plugin with others, see Create and distribute a plugin marketplace."* It is a **per-session flag**, not a persistent install mode — it does not describe or replace the marketplace-install path blackhole's own `CLAUDE.md` documents (`/plugin marketplace add` + `/plugin install`).
- **`claude plugin init`** creates a "skills-directory plugin" at `~/.claude/skills/<name>/`, which "loads as `<name>@skills-dir` with no marketplace or install step" — this is a different plugin-authoring pattern (single-user, no marketplace) and not documented as applicable to a marketplace-distributed, multi-consumer plugin like blackhole.
- **No documented symlink-based or content-watching live-reload exists for a marketplace-installed plugin.** A `source: "."` marketplace entry (blackhole's actual configuration, per ADR-009) is installed the same way as any other marketplace plugin — copied into `~/.claude/plugins/cache/<marketplace>/<plugin>/<version>/`, not used in place, not symlinked. The docs state this explicitly: *"Plugins are copied to `~/.claude/plugins/cache` rather than used in place, except for `command` sources in link mode."* `source: "."` is not a `command` source, so link mode does not apply. **The documented update path for blackhole's actual install mode is therefore identical to Q1/Q2's version-bump-driven mechanism — there is no separate "local/dev git source" fast path once a plugin is installed via the standard marketplace flow, only the `--plugin-dir` per-session dev-testing flag as a wholly separate mode of running Claude Code.**
