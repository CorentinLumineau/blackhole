# Plan: ratio-based linearity tests (issue #1358)

## Objective

The "parsers stay linear" hook tests assert absolute budgets through `minMs(...)` (`scripts/lib/test-fixtures.ts:100`), for example "within 250 ms". An absolute budget measures runner load, not complexity: PR #1356 failed at 1059 ms without touching the guard, and the same evaluator measured 156-220 ms in the same process. Replace every such in-process absolute budget with a growth-ratio assertion: time the same evaluator at size n and 4n in one process, and fail only when the cost grows super-linearly.

Scope: test files plus the shared helper. No guard source (`templates/hooks/pretooluse/**`) changes; that source is held by PR #1334.

Track: Standard (multi-file, shared helper, mutation evidence). Base: `plan_base_commit` b3cedb75a8c3c2444a09b6e240260667167fd2f9.

## Design

One helper in `scripts/lib/test-fixtures.ts`, next to `minMs` (V-INT-02/V-DRY-01: `minMs` already is the shared timing primitive; the new helper is built on it, not beside it):

```ts
expectLinearTime({
  build: (n: number) => input,          // input of size proportional to n
  run: (input) => void,                 // the evaluator under test
  n: number,                            // base size; the test passes the production cap / 4
  factor = 4,                           // large input = build(n * factor)
  runs = 5,                             // minimum of `runs` after a warm-up
})
```

Algorithm:
1. Build both inputs up front (construction time is excluded from timing).
2. `t1 = minMs(() => run(small), runs)`, `tN = minMs(() => run(large), runs)`. The two measurements are taken back to back in the same process, so both see the same JIT state and a similar load level.
3. `ratio = tN / max(t1, FLOOR_MS)` with `FLOOR_MS = 1`. Assert `ratio < MAX_RATIO` with `MAX_RATIO = 12`.
4. On failure the message prints n, 4n, t1, tN and the ratio so a flake is diagnosable.

Why 12: with a 4x size step a linear parser gives a ratio of about 4 and a quadratic one about 16. The original limit 8 (the geometric midpoint 5.7 pushed up) flaked on the shared CI runner, where linear parsers measured 9-10 because the larger input pays extra GC and cache cost; 12 sits above that and below the quadratic 16. The shipped value and its rationale live on the `expectLinearTime` JSDoc in `scripts/lib/test-fixtures.ts`. It cannot catch O(n^1.5) (ratio 8) and, at 12, only a regression that costs several times the fixed per-call cost at 4n (seconds-scale) is guaranteed to fail; the historical regressions (#1183, #1184, #1222, #1239, #1252, #1195, #1197) were all quadratic or worse and seconds-scale, which is what the tests guard.

Why a floor: when `t1` is sub-millisecond, dividing by it measures timer noise. Flooring the denominator at 1 ms means a quadratic input must reach tN >= 12 ms to fail; a quadratic regression whose large input costs under 12 ms is below the 5 s hook timeout by three orders of magnitude and is not what these tests defend. To keep the floor from masking regressions, each test picks `n` so that `build(4n)` is the production worst case (the 32 KiB cap), and the mutation evidence (AC-4) shows each test fails with a quadratic term that is realistic, not an absurd one.

Why min-of-5 and same-process: the minimum discards scheduler preemption, the dominant load effect (one preempted run can be 5x). Ratio-of-minimums cancels a uniform slowdown (CPU frequency, shared core) that an absolute budget cannot. Residual risk: load that changes between the two measurements; mitigated by measuring back to back and by `runs = 5`. If CI still flakes, the helper retries the pair once before failing (decision below).

Retry: on a first failing ratio, re-measure the pair once and fail only if both pairs exceed `MAX_RATIO`. A real quadratic fails every time; a load spike rarely hits two consecutive pairs. Cost: at most 2x the timing of a failing test.

Rejected alternative (the harder path, kept as a follow-up): count parser steps through an injected counter. It is deterministic and load-proof, but it needs a hook in the guard source (`templates/hooks/pretooluse/utils/*.js`), which PR #1334 holds, and it would couple tests to implementation structure and miss regexes whose cost is inside the engine (#1195's `SECRET_KV` backtracking has no step counter to read). Ratio timing works on the unmodified black box today. Revisit once #1334 merges.

## Decision Record

- Context: absolute wall-clock budgets in 12 linearity tests flake on loaded runners.
- Alternatives: (easy) raise every budget 4-10x; (hard) deterministic step counters in the guard; (chosen) same-process n/4n ratio with a noise floor.
- Choice: ratio helper.
- Rationale: raising budgets keeps measuring load and weakens the regression signal (a 2.5 s quadratic would pass a 4 s limit); step counting is the best end state but touches held guard source and cannot see inside regex engines. The ratio asserts the property the tests are named for.
- Confidence: Medium-High; the threshold is validated empirically by AC-4/AC-5.

## Codebase Conventions

- Tests load the guard via `require(path.join(PRETOOLUSE_HOOKS_DIR, 'utils', ...))` and wrap fixtures in `withLinkedWorktree`; keep that shape.
- Timing helpers live in `scripts/lib/test-fixtures.ts` (`minMs`, V-INT-02: extend, do not add a parallel helper file).
- Comment discipline: rationale lives once, on the helper's doc comment; call sites reference `expectLinearTime` by name, no issue numbers in comments (a test title may keep its `#NNNN:` prefix).

## Execution Strategy & Stop Conditions

- If the ratio for an unmutated test exceeds 12 in two clean (unloaded) runs, stop and re-derive `n` for that test (the input likely has a non-linear but legitimate component, e.g. a PATH_MAX-bounded tree) rather than raising the threshold.
- If any converted test does not fail under its mutation, abort that conversion and revert it to its old form, filing the gap in the PR body.
- If a test cannot scale 4x (row 6: depth bounded by PATH_MAX), stop and use factor 2 with `MAX_RATIO` 3 for that call only, documented at the call site.
- If a guard source edit seems necessary, abort and halt: that source is held by PR #1334.

## Risks

- Row 6: depth is capped by PATH_MAX (~4096), so `4n` must be at most about 3,800 characters; base `n` is about 950 characters, where the walk is near 1 ms. The floor handles it; its mutation must be strong enough to cost over 12 ms at depth 4n.
- Row 11 (5 ms regex budget on 2,400 chars): at this size `t1` is far below the floor. Scale it to n=600 / 4n=2,400 and rely on the mutation proof; if the regex backtracking cannot be separated from noise at this size, enlarge both sizes (the quadratic-regex failure mode in #1195 is visible well beyond 2,400 chars).
- V-TEST-11 (unfalsifiable test): the mutation evidence in task 5 is the guard against shipping a ratio test that cannot fail.

## Open questions

1. Should the subprocess `elapsed < 2500` / `< 4000` end-to-end deadline tests get a separate, looser treatment (for example 2x the current value, or a retry)? They encode the 5 s hook-timeout contract, so they are left out of this issue.
2. Keep a very loose absolute backstop (for example one second per evaluator call, well under the 5 s hook timeout) in addition to the ratio? Default: no; the ratio plus mutation evidence is the stated acceptance in the issue.
