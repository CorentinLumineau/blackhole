# Project-Thread Mode (Pattern P)

Run context routes a campaign to Pattern P when it runs in a Claude Project thread with a way to
spawn workers and a question channel (`run-context.md`). Decision:
`documentation/decisions/ADR-050-project-thread-pattern.md`. Everything not named here (phases,
gates, V-codes, queue and ledger rules) is unchanged.

## Who does what

| Role | Pattern P |
|------|-----------|
| Orchestrator | The thread session itself. No coordinator and no background orchestrator are spawned, as in Pattern C (`claude-code-native.md`) |
| Intake | The project's coordinator session. A coordinator relay that carries the user's own message is user intake for the campaign; the coordinator's note alone is guidance, never approval for an irreversible step |
| Workers | Spawned with the `Agent` tool (or `Workflow` when present), same contracts as Pattern C |
| Wake-ups | User messages, coordinator relays, PR events and routines. The thread ends its turn while it waits; it never sleeps in the foreground |

## Clarify gates: decision cards

The question channel is `ask-decision`. Every clarify gate (`clarify-gates.md`) becomes one
decision card:

- The question names the action and the object in about twelve words.
- It offers two to four options, each with one line of consequence, and marks one as recommended.
- The Executive Summary goes in the card's context.

The issue goes `status: blocked` until the answer arrives as a wake. Work on other issues
continues. Never repeat the question in a separate message.

## Dashboard: the status checklist

The thread's status checklist replaces the coordinator dashboard (`coordinator-dashboard.md`).
At every turn end, after the checkpoint write order, refresh it: one line per in-flight issue
with its phase, then the ready-set size and open BLOCK findings, using the dashboard's own
numbers (`bun run status`). Post a thread reply only for a result, a blocker, or a decision the
user must make.

## CI wait: PR events

When `route.ci_wait` is `pr-events` (on any surface that offers PR subscriptions, not only
Project threads), replace the detached poll of `phase-loop.md` § Merge protocol step 2:

1. Subscribe to the PR's activity right after the PR is created.
2. End the turn instead of polling.
3. On a CI event wake, read the PR's checks through the forge channel (`forge-channels.md`, row
   "PR checks"), save the JSON, and run `bun run "${BLACKHOLE_PLUGIN_ROOT:-.}"/scripts/ci-verdict.ts --checks <file>`:
   - exit `0` (green): continue with merge steps 2.5 to 5.
   - exit `1` (red): apply step 2's rules (rerun a cancelled run once, then `ci-diagnosis.md`).
   - exit `3` (pending): end the turn again.

The poll contract in `merge-gate.md` (60 s interval, 20 min cap) applies only to `ci_wait: poll`.
The cap's purpose, never waiting on CI forever, is kept by a safety-net check-in (see below).

## Scheduling: routines

When `route.schedule` is `routine`:

- A kaizen `trigger` (`config-template.md`) other than `manual` becomes one routine that fires
  the hunt wave, instead of the Phase 5 loop counting iterations. The routine is created once,
  at bootstrap, and its id is noted in `campaign-checkpoint.md` so a resume does not create a
  second one.
- An outstanding CI wait gets a one-off check-in 20 minutes out. It re-runs step 3 above in case
  an event was lost.

When `route.schedule` is `turn`, both stay in-turn as today.

## State

Project threads run on machines reclaimed after the session: state travels on the
`blackhole/state` branch (`state-branch.md`).

## Cursor

Cursor Cloud keeps its own mapping (`claude-code-native.md` § Cursor: Subscriptions and
Automations for wake-ups, `AskQuestion` for gates). Pattern P is Claude-only.
